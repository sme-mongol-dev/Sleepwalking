## Platform and beam follow-up

Level Design's readability pass exposed three integration questions. The timed platform used a fixed 65% duty cycle even though L05 authors `ActiveSeconds = 2.8` and `CycleSeconds = 4`. The mechanism now uses `ActiveSeconds` clamped to the cycle and retains `PhaseSeconds` across retry. The moving platform previously updated its Transform in `Update` and began at the path midpoint. It now has a kinematic `Rigidbody2D`, moves from its authored position in `FixedUpdate`, and conveys a player contacting its top. Rider speed is cleared on side contact, exit, impact, and reset. A shared zero-friction physics material prevents contact friction from adding a second horizontal carry. The moving prefabs currently author phase zero; the mechanism deliberately starts them at the authored position regardless of `PhaseSeconds`.

`SleepwalkingGame.BeamWidth()` already reads the active `GameCamera.targetTexture.height`; the earlier report that it always divides by 180 is stale. `UpdateBeamWidths()` runs while a dream is active. The intended width remains 3.5 pixels at both 320×180 and 320×240.

The first physical PlayMode run (`Docs/QA/mechanism-physics-results.xml`) passed BeamWidth and L05 but found a `MissingComponentException` in the new L06/L07 platform setup: C# `??` did not respect Unity's fake-null component semantics. Two explicit Unity `== null` checks corrected it. The rerun (`Docs/QA/mechanism-physics-rerun-results.xml`, `mechanism-physics-rerun.log`) finished with **3 Passed, 0 Failed, 1 Ignored** and Unity code 0. Passed cases cover L05 authored 2.8/4-second on/off/on, L06 horizontal and vertical rider contact and relative movement, reset to authored start, and 3–4 rendered pixels at both RenderTexture heights. L07 is Ignored because its authored geometry has no MovingPlatform; L06 covers both movement axes. The independent Mechanics lead audited XML, log, source, and the skip condition and accepted the fix.

This test calls game state through PlayMode and places the player on a platform; it does not establish keyboard-controlled traversal, real trap contact, visual quality, audio, or packaged Player behavior. The follow-up Windows Player was rebuilt with these changes (`Docs/QA/VisualLogs/RoomLogoIntegratedMainBuild.log`: `Windows build: Succeeded 0 errors`; managed assembly updated at 03:51), but its mechanics have not been interactively verified in the packaged Player.
