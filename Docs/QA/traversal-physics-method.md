# Проверка физических маршрутов L01–L07

Дата подготовки: 14.11.2026. Область QA: `Assets/SleepwalkingTests/PlayMode/` и `Docs/QA/`. Параметры `SleepwalkingPlayer`, геометрию, коллайдеры и prefab assets меняют владельцы Mechanics и Level Design. Этот документ задаёт метод; результатов прохождения пока нет.

## Входные данные

Для каждого из 2–3 профилей нужны точные значения `RunSpeed`, `GroundAcceleration`, `AirAcceleration`, `JumpSpeed`, `GravityScale`, `DashSpeed`, `DashSeconds`, `WallSlideSpeed`, `CoyoteSeconds`, `JumpBufferSeconds`, `DashCooldownSeconds`. Mechanics подготовил `SleepwalkingMovementProfile` и генератор трёх кандидатов; перед прогоном требуются созданные `.asset` и таблица обязательных переходов от Level Design. Для каждого перехода нужна строка с уровнем, исходной и целевой платформой/маркером, требуемым навыком, допустимой фазой механизма, ожидаемым запасом приземления и запрещённым обходом. Номер версии prefab/профиля фиксируется до запуска; изменение данных во время прогона делает результат устаревшим.

## Реальный ввод и критерий достоверности

PlayMode загружает `Assets/Scenes/Sleepwalking.unity`, создаёт настоящий сон через `SleepwalkingGame.StartDream()` и использует существующие `SleepwalkingPlayer`, `Rigidbody2D`, `Collider2D` и `SleepwalkingMechanism`. Тест может поставить игрока в документированную исходную точку через `ResetAt()` для отдельного перехода; после этого путь выполняется только вводом. Дополнительно нужен непрерывный прогон каждого L01–L07 от `PlayerStart` до `BedExit`, чтобы отдельные удачные прыжки не скрыли непроходимую связку.

Для физических PlayMode прогонов Mechanics добавил `SleepwalkingPlayer.SetSimulatedInput(horizontal, jump, dash)`. Он подаёт те же команды в штатные `Horizontal()`, `PressedJump()` и `PressedDash()` контроллера, не меняя скорость или координаты напрямую. Перед маршрутом диагностический пробник должен показать: горизонтальная команда реально меняет положение тела, импульс jump вызывает прыжок, dash вызывает `dashRemaining > 0`, `ClearSimulatedInput()` прекращает управление. Если пробник не прошёл, маршрут получает статус **не оценён**; координаты после прямой установки `linearVelocity` или transform не засчитываются. Этот путь доказывает физику контроллера, но не клавиатурную привязку; для последней нужен отдельный Input System/Player smoke.

Время ввода задаётся в фиксированных физических шагах. На каждом `FixedUpdate` записываются индекс шага, `Time.fixedTime`, нажатые клавиши, позиция и скорость `Rigidbody2D`, нижняя/боковая граница `BoxCollider2D`, `grounded`, `wall`, `dashRemaining`, `standingPlatform`, состояние целевого коллайдера и ID контактов. События смерти, появления нового игрока и смены уровня отмечаются отдельно. Трасса сохраняется в CSV/JSON рядом с XML Test Runner и логом Unity; для провала дополнительно сохраняется кадр с позицией камеры. Диагностические private-поля допустимо читать отражением только в тесте, не менять ими физику.

## Проверка одного перехода

1. Записать профиль, сцену, level prefab, стартовую платформу, координаты игрока, скорость и фазу механизма; дождаться устойчивого контакта с исходной опорой минимум три физических шага.
2. Выполнить заявленную последовательность ввода. Для прыжка подтвердить фактический отрыв и положительную вертикальную скорость; для wall jump — контакт со стеной при `!grounded`, импульс от стены и приземление; для dash — вход в `dashRemaining > 0` и пройденное расстояние; для moving — контакт `standingPlatform` и перенос при движении платформы; для timed — реальное включение/отключение коллайдера и пересечение в доступное окно.
3. Успех — контакт с указанной целевой опорой не менее трёх физических шагов, игрок жив, уровень не сброшен. Запас приземления измерять по горизонтальному пересечению границ `BoxCollider2D` игрока и опоры в первом устойчивом контакте: минимальное расстояние до левого/правого края опоры. Записать также расстояние от центра игрока до ближайшего края. Касание на один кадр и пролёт над платформой успехом не считаются.
4. При провале указать конкретное событие: недолёт, перелёт, касание без удержания, удар о стену, падение, ловушка, смерть, неверная платформа, таймаут или сбой ввода. Сохранять траекторию и ближайшую достигнутую точку; один неудачный тайминг не объявлять доказательством непроходимости.
5. Для каждого перехода провести несколько документированных расписаний ввода вокруг ключевых моментов (ранний/средний/поздний прыжок и dash, ранняя/средняя/поздняя фаза moving/timed). Сообщать число успешных попыток и диапазон запаса, а не только лучший результат.

## Обязательный навык и обход

Для перехода с требуемым навыком запустить отдельные попытки с запрещённым действием: L07 без wall jump и без dash по отдельности, L05 без ожидания окна timed, L06 без поездки на соответствующей moving платформе. Иные допустимые действия оставить доступными. Если целевой контакт достигнут, это воспроизводимый обход и дефект требования. Если обход не найден в конечном наборе попыток, писать только «обход не найден при перечисленных сценариях»; конечный поиск не доказывает невозможность любой последовательности ввода.

L01–L04 требуют проверки обычного движения/прыжка и сохранения постепенного ввода шипов, пилы, кнопки/лазера. L05 проверяется на нескольких фазах всех трёх timed платформ, включая исчезновение под игроком. L06 проверяется отдельно на горизонтальной и вертикальной moving платформе, потом на полной связке. L07 — на wall jump, dash через последний разрыв и достижении кровати. Для смерти нужен физический контакт с ловушкой/зоной падения, затем проверка того же уровня, стартовой позиции, работоспособного ввода и сохранённого следа после респавна; переход на следующий уровень при смерти недопустим.

После заявленной Level Design переработки L05/L06 (код генератора изменён около 13:08, префабы ещё пересобираются) регрессия должна работать на **новой сериализованной** геометрии, а не на предположении по исходнику. L05: непрерывная цепь `Start → L05_TimedA → L05_TimedB → L05_TimedC → ExitRun`, на каждой промежуточной площадке устойчивый контакт ≥3 FixedUpdate при включённом коллайдере, запись фаз и остатка активности перед прыжком; после выхода — контакт с кроватью. L06: `Start → L06_Horizontal → LiftLanding → L06_Vertical → HighExit → BedExit`; для обеих moving платформ кроме контакта требуется положительное собственное смещение платформы и сохранение относительной позиции игрока в течение поездки. Прямые прежние маршруты L05 `Start→ExitRun` обычным прыжком и L06 `Start→LiftLanding` без `L06_Horizontal` повторить по тем же профилям/расписаниям и расширить момент прыжка. Отсутствие успеха в этих конечных попытках означает только «обход не найден в выбранном диапазоне».

## Прогоны и вердикт

Порядок: входной пробник ввода → отдельные обязательные переходы для каждого профиля → обходы навыков → непрерывные L01–L07 → выбранные повторения в собранном Windows Player, если тестовый ввод в Player подтверждён. PlayMode/XML без Windows Player не означает ручную приёмку. Не запускать Editor параллельно сборке или захвату другого владельца.

Таблица результатов: `profile`, `level`, `transition`, `start`, `target`, `requiredSkill`, `inputTrace`, `mechanismPhase`, `landed`, `landingMargin`, `deathOrReset`, `bypassVariant`, `attemptCount`, `evidencePath`, `status`. Статусы: **пройден**, **провален**, **обход найден**, **не оценён**. Оценка геометрии и статичный кадр могут объяснить результат, но не заменить трассу реального контроллера и контактов. Конкретный провал передаётся владельцам Mechanics/Level Design вместе с профилем, уровнями, шагами ввода и артефактами; после исправления повторяется тот же сценарий и соседние переходы.
